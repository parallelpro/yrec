# core/ — the star layer: the run, the step and the structure solve

This directory drives a YREC run and evolves the model. It owns the model state (`star%`, declared in `state/star_info_lib.f90`) and calls the physics domains (eos, kap, atm, net, convection, rotation, element_diffusion) and the numerics through their public modules.

Its subdirectories follow the layers of `docs/TARGET_ARCHITECTURE.md` §4.1:

```
  run/          the run: controls, tables, run cards, calibration, Monte Carlo, stops
    step/       one model: the stages in order, and the next timestep
      structure/    the Henyey solve of the structure equations
      envelope/     the outer layers: atmosphere and envelope integrations
      model/        the model itself: the starting model, rescaling, rezoning
    diagnostics/  the converged star: the stitched model and derived quantities
```

`main.f90` is the command-line entry point; `run/yrec_capi.f90` is the same engine for C and Python (`pyyrec`). Paths below are under `src/` unless they start at the repository root.

## 2. The flow

### 2.1 The run

`run_yrec` (`run/run_driver.f90`), called by `main.f90` and by the C entry `yrec_run`, runs one job:

1. `yrec_run_prologue` (`run/yrec_reset.f90`): the run's star, a copy of the process-start star; at a re-entry, the previous run's log and final-model units closed first (`close_run_units`).
2. `read_controls` (io): the controls into `s%control` and `s%physics`, and the run plan.
3. `open_run_files` (io): the run log, the copy of the deck, the starting and final models, the Monte-Carlo and isochrone files; `output_open` (io): the history and profile output.
4. `prepare_run` (`run/run_setup.f90`): the run plan's envelope Z; the solar units, log10 G, the kap/eos/atm settings and tables; the Monte-Carlo samples. Then `warn_inconsistent_controls` (io).
5. For each Monte-Carlo run (`first_mc_run` to `last_mc_run`; one run without Monte Carlo):
   1. `begin_monte_carlo_run` (`run/monte_carlo.f90`): every run copy of a control re-armed, the state a run leaves cleared, the run's samples applied; `install_monte_carlo_settings` (setup).
   2. `begin_calibration`: `setup_solar_calibration` or `setup_star_calibration` (`run/calibration.f90`) lay out the run cards.
   3. For each run card: `begin_kind_card` (the card's composition and mixing length, `install_card_settings`, `read_starting_model`, `initialize_turnover_timescale` (the starting model's stitched model and turnover time), `check_rotation_initialised`, `init_stop_conditions`, the neutrino table, the output headers, `locate_shell_boundaries`, `compute_timestep`); then `evolve_step` (§2.2) up to the card's model count, until a stop (`step_kind_card_done`) or the star calibration's crossing of R* (`step_leave_run_loop`, which goes on to the next card); `end_kind_card`; `end_of_card_calibration` (`check_solar_calibration` after each triple, `end_star_calibration_card`), which may end the card list.
   4. `log_run_summary` (io): why the run ended (`s%termination_reason`) and the final model; `write_run_summaries`: the Monte-Carlo summary.
6. `output_close` (io).

The stops (`run/stop_conditions.f90`, `check_stop_conditions`, after each converged model is written): the end age, the central D/X/Y table, the structure limits, then the star calibration's target radius.

### 2.2 A step

`evolve_step` (`step/step_driver.f90`) advances the model by one timestep:

1. **Mass and composition** (`advance_composition_and_age`): the mass change (`change_mass`), then the composition step over the timestep (`advance_composition`'s predictor pass), and the new age.
2. **The mesh** (`rezone_or_snapshot`): the rezone, and the start-of-step snapshot.
3. **The structure** (`solve_structure`): the Henyey solve in levels. Level 1 uses the previous model's envelope triangle; level 2 checks the surface boundary first; level 3 follows, and from level 3 on the composition step is redone before each solve (`solve_level`: `refresh_surface_bc`, the corrector pass, then `henyey_iterate` on the equations of `compute_henyey_coefficients`).
4. **Level 4 and rotation** (`converge_with_rotation`): level 4 runs for every model, inside the structure-rotation iteration, which has one pass without rotation; then the convergence verdict, the convection zones mixed fully and, with rotation, the angular momentum (`evolve_angular_momentum`) and the shape factors.
5. **After convergence:** the shell boundaries (`locate_shell_boundaries`), the light elements (`burn_light_elements`), the envelope rebuild after accretion (`rebuild_envelope_after_accretion`), the next timestep and the model's count (`set_next_timestep`: `compute_timestep`), the stitched model (`build_stitched_model`), the observables (`compute_observables`), the turnover time (`refresh_turnover_timescale`), the output (`output_write_model`), and the stop conditions (`check_stop_conditions`).

Each stage is a module procedure of `step_driver` that takes the star, the step's record and `ierr`. The record, `step_state`, holds what one stage hands another and nothing else: whether the model is aged this step (`evolve_model`), the accretion's request to rebuild the envelope and its target mass, the surface convection zone's base at the start of the step, and the solve's iteration count and verdict. `evolve_step` makes a new one at every call.

The observables fill the output's quantities; one of them is model state as well: `renormalize_luminosity_breakdown` rescales `luminosity_breakdown_lsun` after the step's `compute_timestep` has read the solver's values, and the rescaled values are what the model file stores and what the next card's first `compute_timestep` reads (the factor is 1 to within the solver's last correction; bug_sweep M333). The turnover time, which the next step's deuterium cap and wind read, is a stage of the step: `refresh_turnover_timescale` walks the stitched model (`compute_turnover_timescale`) and copies the turnover time and `photosphere_logP` to their `_prev` members, the start values the wind interpolates from during the next step. The walk also writes the radius of the convection zone's base it finds into `envelope_radius_rsun`, over `compute_observables`' value, so the output has the walk's. For a card's starting model `initialize_turnover_timescale` does the same after `read_starting_model`.

A step that diverges stops the run: nothing cuts the timestep. `physics%solver_max_correction` (0 = off, the default) limits what one Newton pass may change: no shell's log P, log T or log R by more than it (`set_henyey_correction_factor`), for a model far from a solution (a rescaled model's first steps).

## 3. Conventions

- **The star comes in as an argument:** a core procedure that touches it takes `type(star_info), intent(inout) :: s` first and reads `s%member`. `run_yrec` owns the run's star (there is no global one since 2026-10) and passes it down; `yrec_reset`'s prologue resets it to its process-start state at the start of every run. A driver reads the model from the star; it takes the model's arrays as arguments only when its callers pass different models (`burn_li_be` and `store_end_li_be_rates`: the converged model or a rotation sub-step's; `advance_composition`'s zone outputs at the corrector passes), and its header says so.
- **Kernels** take no star (star rule 6) and print nothing. Fifteen files are star-blind (`tools/check_boundaries.py`'s `STAR_BLIND_FILES`): `shell_equations` and `triangle_fit` (structure/); `mass_change_kernel`, `composition_kernels`, `li_be_burn` and `timestep_limits` (step/); `envelope_integration_kernel`, `envelope_integrands` and `envelope_refit_kernel` (envelope/); `regridding`, `rescaling_kernels`, `mesh_spacing` and `core_extension` (model/); `turnover_walk` and `stitched_kernels` (diagnostics/). `find_shell_boundaries`, `henyey_eliminate`, `henyey_solve` and `convection_geometry`'s procedures but `locate_surface_mixing_base` are star-free procedures in files that also hold a star driver. Their drivers gather from the star and store back. A new kernel's file goes in `STAR_BLIND_FILES`, with ok/FAIL checks in a test program and their mutations (§4; §6, "Add a kernel with its test program").
- **Steps with arguments:** `rezone`, `read_starting_model`, `rescale_model`, `build_stitched_model`, `henyey_iterate`, `evolve_step`, `apply_mass_change` and `advance_composition` are drivers whose steps are module procedures with explicit arguments (the star, the driver's state record where it has one, `rezone_state`, `starting_model_state`, `rescale_state` or `step_state`, documented at its type, and `ierr`); everything else a step needs is its own local. `compute_timestep`'s steps are too, but for `take_tightest_limit`, the one line that lists its host's limits; the turnover walk's steps take arrays and a `zone_search` record; the envelope kernel's take its `integration_state`. `run_yrec`'s four steps are internal procedures on its static locals.
- **Units:** CGS unless a name carries its unit (`_msun`, `_lsun`, `_yr`, `_gyr`); `log` is log₁₀.
- **The structure variables** are log₁₀ P, log₁₀ T, log₁₀ R and L in L☉, against log₁₀ m. The difference equations and their partials follow `docs/TARGET_ARCHITECTURE.md` §4.4 and `shell_equations`' header.
- **The aging flag** (`step_state`'s `evolve_model`) marks a model solved but not aged (on a rescale card); `s%dt` is negative only when a model file stores a negative timestep, and `compute_timestep` keeps its magnitude.
- **Errors:** a procedure that can fail returns `ierr` up to `run_yrec`, which returns it: `main` exits 1 on a positive `ierr`, and `yrec_run` returns it to C. The one negative code is `envelope_termination` (-2, `envelope_integration_kernel`): a Bulirsch-Stoer step of the envelope integration underflowed, the historical "solution diverged" end, after which the outputs up to that model are valid and `main` exits 0. The kernels' own codes (`numerics_bad_input`, `numerics_singular`, the eos and kap codes) pass through unchanged, an EOS or opacity failure inside a Bulirsch-Stoer step of the envelope integration included (bug_sweep M132). `yrec_run` refuses a namelist path longer than 256 characters with 1, before anything runs. A NULL path is read as an empty one, the default deck name (but see bug_sweep M384: an empty path falls back to the host's first command-line argument). An atmosphere whose start lies past the photosphere at each of `max_start_tries` (12) starting densities returns `ierr = 1` with the event `envint_start_exhausted`. `build_stitched_model` returns the code of a failed output envelope integration (bug_sweep M327): a positive one stops the run, `envelope_termination` ends it as the solver's does.
- **Messages** go through `core_messages`, never through a `write` of core's own. The caller formats into an array of lines (`character(len=message_length) :: lines(n)`, set to `unwritten_line`, then an internal write) and calls one route: `core_report` (the terminal and the run log: an error the run stops on, or a warning it goes on with), `core_terminal` (what the F77 `write(*)` meant: standard output once io assigns the units, standard error before) or `core_log` (the run log: the per-model notes and the solver diagnostics). An error's text begins "ERROR: ", a warning's "WARNING: ", then where it comes from ("starting model: ", "rezone: ", "envelope integration: ", ...), in sentence case; an error the run stops on ends "; run stopped". A line whose form a route would change has its own procedure: the list-directed lines go through `core_terminal_values` and `core_log_values`, which keep their trailing blanks, and the composition step's mixed zones through `log_mixed_zone_bounds`. The kernels print nothing: `integrate_envelope_atmosphere` returns events and `atm_get` reports them; `henyey_eliminate` and `henyey_solve` return `numerics_singular` and their drivers report it. `check_boundaries`' `check_no_io` keeps the files of `STAR_BLIND_FILES` and core's entries in `KERNEL_FILES` (`shell_boundaries`, `model_rescaling`, `calibration`, `observables`, `turnover_timescale`, `stitched_model`) free of I/O statements. The I/O core keeps is file handling: the starting model's `rewind` (`starting_model`) and `close_run_units`' inquire and close (`yrec_reset`); the Monte-Carlo files are read, written and rewound by `io/monte_carlo_files`.
- **Controls:** core is the star layer, so its drivers read `s%control` and `s%physics` directly (io/README.md §5, "Add a control the star layer reads directly"); its kernels take what they need as arguments or in a settings record (`timestep_settings`, which `timestep_settings_of` builds from the star). The physics domains read only the settings records that `setup/` builds.
- **Kept by decision:** the extra energy sources' registry is the process's configuration, not model state, and outlives `run_yrec` until `clear_energy_sources` (`energy_sources`' header); `run_yrec`'s locals, its star among them, are static (a blanket `save`), and the prologue resets the star; a diverging step stops the run (§2.2); `envelope_termination` exits 0, as the F77's "solution diverged" did.

## 6. How to extend

**Add an energy source** (tidal heating, magnetic heating, an injected energy), with no edit of YREC's source:
1. Write the source as a subroutine with `energy_sources`' interface, `subroutine my_source(pt, eps, deps_dlnrho, deps_dlnt, ierr)` with `type(energy_point), intent(in) :: pt` (m, dm, log T, log P, log rho, log r, L, xa, dt): eps in erg/g/s, its partials at constant T and at constant rho, `ierr` nonzero to stop the solve.
2. In a program, register it before the run, `call add_energy_source('name', my_source, ierr)`, then `call run_yrec(ierr)`: `examples/other_energy/yrec_extra_heat.f90` is the template, and `make other_energy` in `src/` the build rule to copy.
3. The term enters the luminosity equation at every interior shell (`evaluate_shell_equations`' step `form_extra_energy_terms`), its partials the Jacobian, and its luminosity the history column `lum_extra`. A source above the fitting point has no effect (the envelope is integrated at constant L).
4. Test it: register it in a copy of `test_structure`'s `extra` case (module `test_structure_source`) to check its partials against finite differences, and run a deck as `test_other_energy.py` does.

Traced (2026-11-12, in a scratch copy of the tree): a program that registers a constant 1 erg/g/s source before `run_yrec`, linked as `make other_energy` links `yrec_extra_heat`; cm_base's history column `lum_extra` is 0.5191 Lsun, M/Lsun for 1 erg/g/s.

**Add a timestep limit:**
1. In `core/step/timestep_limits.f90`, a kernel: a function of the settings record and the arrays it needs, returning the limit in seconds, `dt_unlimited` when it does not apply (and never a negative value: a ratio that cannot be formed is `dt_unlimited`); its name in the module's `public` list. A setting it needs goes in `timestep_settings` and in `timestep_settings_of` (`timestep_control.f90`), from a control (a new control is io/README.md §5's recipe).
2. In `compute_timestep` (`timestep_control.f90`): the kernel's name in the `use timestep_limits, only:` list, a local for its result, the call after the other limits, and the result in `take_tightest_limit`'s list (one line).
3. In `core/test/test_timestep_limits.f90`, a check of its formula and of its switch, and a mutation of each in `test_timestep_limits.mutations.toml`. Then `make tests`, regenerate the pinned output that `test_timestep_limits.py` byte-compares (`./test_timestep_limits > core/test/expected_test_timestep_limits.out` in `src/`: only your new lines may differ), and `python3 src/tools/mutate.py core --program test_timestep_limits`.
4. `python3 -I tools/check_star_contracts.py --fix` in `src/` when the setting reads a star member that `timestep_settings_of`'s or `compute_timestep`'s contract does not list yet, `python3 -I tools/gen_star_docs.py`, then `make check`.
5. This README: the test table's row (its count of mutations) and the total in §4.
6. Re-pin what moves (every deck where the limit binds), in a measured commit.

**Add a kernel with its test program.** A kernel is the arithmetic of a driver, on arrays and small records, with no star and no output; `core/step/li_be_burn.f90` with `core/test/test_li_be_burn.f90` is the example to copy.
1. The kernel: a module in the directory of the driver that calls it, `private` with a `public` list, its procedures `pure` where they can be, the thresholds named parameters with their units, the inputs `intent(in)`. What it needs from the star arrives as arguments (arrays, scalars, or a small record type the module declares, as `mixed_region_bases`); it has no `use star_info_lib` beyond the layout's constants (`composition_layout`), no `write`, no `stop`.
2. The driver gathers from the star, calls the kernel and stores the results (`burn_step`'s `burn_li_be`); its header says which module holds the arithmetic.

**Add a mesh criterion.** The rezone keeps the flagged points and spaces the new mesh evenly in chi between them (`model/rezoning.f90`). 1. Write the step beside the others, taking the star and the rezone's state:
   ```fortran
   ! ---------------------------------------------------------------
   ! The first point where L reaches half the surface luminosity.
   !   star reads: none
   !   star writes: none
   subroutine flag_half_luminosity(s, rz)
         type(star_info), intent(inout) :: s
         type(rezone_state), intent(inout) :: rz
         integer :: i
         do i = 2, s%nz
            if (s%luminosity_lsun(i) >= 0.5_dp*s%luminosity_lsun(s%nz)) then
               call append_flag_point(rz, i)
               exit
            end if
         end do
   end subroutine flag_half_luminosity
   ```
2. Call it in `flag_fixed_points` before `sort_flag_points`, and name it in the list in that procedure's header. The list holds `max_flag_points` (100); `append_flag_point` drops and reports (once per rezone) what does not fit, so call a criterion that must win before the scan of jumps (`flag_jumps`).
